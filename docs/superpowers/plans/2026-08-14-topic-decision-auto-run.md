# Topic Decision Automatic Run Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make one `Start analysis` click synchronously run positions, decisionability, debate, and proposal synthesis, then display either evidence questions or proposals.

**Architecture:** Keep the backend state machine unchanged. Add a small Viewer-side orchestration function that always reloads the decision detail between mutations and uses the returned `session.version`; stop on evidence-blocked or terminal states. Reuse the existing renderer, error surface, in-flight guard, authentication, and HTTP routes.

**Tech Stack:** TypeScript, inline browser JavaScript generated by `Memory/src/viewer/static.ts`, Vitest, Docker Compose, Chromium browser verification.

## Global Constraints

- Automatic progression ends after proposal generation; proposal approval and execution confirmation remain manual.
- The UI uses synchronous waiting with visible progress; no background job or polling API is introduced.
- Every mutation carries `namespace`, the latest `expectedVersion`, `adapterId: "memory-console"`, and a click-scoped unique `requestId`.
- Session versions are read after each mutation; they are never predicted.
- Stop states are `gathering_evidence`, `awaiting_user_input`, `blocked_by_evidence`, `blocked`, `stale`, `failed`, and `cancelled`.
- HTTP 409 reloads the latest detail and stops the chain.
- Existing named Docker volumes must be preserved.

```js
const topicDecisionStopStates = new Set(["gathering_evidence", "awaiting_user_input", "blocked_by_evidence", "blocked", "stale", "failed", "cancelled"]);

function renderTopicDecisionProgress(step) {
  $("topicDecisionDetail").classList.remove("hidden");
  $("topicDecisionBody").innerHTML = '<div class="decision-progress"><strong>Analyzing topic</strong><div>' + esc(step) + '</div></div>';
}

function readTopicDecisionDetail(sessionId, namespace) {
  return api("/api/v1/topic-inbox/decisions/" + encodeURIComponent(sessionId) + "?namespace=" + encodeURIComponent(JSON.stringify(namespace)));
}

function topicDecisionMutationStep(sessionId, action, expectedVersion, namespace, requestId) {
  return api("/api/v1/topic-inbox/decisions/" + encodeURIComponent(sessionId) + "/" + action, {
    method: "POST",
    body: JSON.stringify({ namespace, expectedVersion, adapterId: "memory-console", requestId })
  });
}
```

- [ ] **Step 5: Implement ordered orchestration using refreshed versions**

Add:

```js
async function runTopicDecisionPipeline(sessionId, namespace, requestPrefix) {
  let detail = await readTopicDecisionDetail(sessionId, namespace);

  renderTopicDecisionProgress("Gathering positions");
  await topicDecisionMutationStep(sessionId, "run", detail.session.version, namespace, requestPrefix + "-run");
  detail = await readTopicDecisionDetail(sessionId, namespace);
  if (topicDecisionStopStates.has(detail.session.state)) return detail;

  renderTopicDecisionProgress("Running debate");
  await topicDecisionMutationStep(sessionId, "debate", detail.session.version, namespace, requestPrefix + "-debate");
  detail = await readTopicDecisionDetail(sessionId, namespace);
  if (topicDecisionStopStates.has(detail.session.state)) return detail;

  renderTopicDecisionProgress("Generating proposals");
  await topicDecisionMutationStep(sessionId, "proposals", detail.session.version, namespace, requestPrefix + "-proposals");
  return readTopicDecisionDetail(sessionId, namespace);
}
```

Update `openTopicDecision(topicId)` to create/reuse the session, render initial detail, invoke the pipeline with a single timestamp-derived prefix, and render the returned detail. Preserve its existing `finally` block so controls are restored.
