# Upstream v1.1.1 Convergence Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use `executing-plans` to implement the core path in order: Phases 1–6, 8–10. Stop at every phase gate; do not continue after a failed gate. Phase 7 is explicitly deferred until the core cutover and upstream intake loop are stable.

**Goal:** Rebase the long-lived `bluewatercg/memmy-agent` product line onto an upstream release baseline, adopt upstream implementations by default, preserve only fork-specific behavior with explicit contracts, and cut over without modifying or downgrading the existing fork v11 database.

**Architecture:** Build a new convergence branch from an immutable upstream release tag, not from the current fork branch. Treat upstream Memory, Agent, User Memory, project environment, retrieval, Goals, model workspace, and migrations as canonical. Forward-port fork-only behavior behind existing upstream seams; migrate data through an offline, version-aware export/translate/import path into a new database. Keep the current `dev` deployment and database untouched until final cutover.

**Tech Stack:** TypeScript, Node.js 20+, Vitest, better-sqlite3/sqlite-vec, Electron, Docker Compose, npm workspaces.

---

## Decision and safety proof

### Confirmed safe path

1. Pin an immutable upstream release tag and create a separate worktree from it.
2. Convert fork behavior into black-box contract tests before porting implementation.
3. Keep upstream implementations whenever they satisfy those contracts.
4. Forward-port only missing behavior, module by module, behind upstream interfaces.
5. Never open the fork database with upstream code. Fork schema is v11; upstream v1.1.1 schema is v6 and rejects newer versions.
6. Migrate into a newly created upstream database through a tested translator. Preserve the original database and a lossless archive of fork-only tables.
7. Shadow-verify the candidate with production-shaped data before switching any client configuration.
8. After convergence, consume future upstream releases as small, regular merges instead of accumulating another multi-month fork delta.

### Rejected paths

- **Direct merge `origin/main` into `dev`:** mechanical trial reports 86 conflicts across Memory schema, repositories, retrieval, sessions, Agent integrations, UI, packaging, and tests.
- **Rebase all 146 fork commits onto upstream:** preserves historical implementation choices instead of choosing the better implementation; many commits overlap upstream features.
- **Open or downgrade the v11 SQLite database with upstream v6 code:** upstream rejects versions greater than its schema version; down migration does not exist.
- **Copy upstream subsystems into current `dev`:** keeps the fork as the architectural base and guarantees continued divergence.
- **Permanent dual-write:** creates two authorities and complex failure ordering. Use snapshot/delta migration and a short write freeze instead.

### Anti-pattern guards

**Steps:**

### Task 20: Cut over with a write freeze

**Steps:**

1. Stop all Memory writers and verify no open write sessions remain.
2. Hash and preserve the original v11 database, WAL/SHM state after checkpoint, config, and fork-only archive.
3. Run the final migration into a new candidate database.
4. Start the candidate on non-production ports and run the full smoke path.
5. Atomically switch client endpoint/configuration; do not overwrite the old database.
6. Keep the old deployment stopped but immediately restartable.
7. During the rollback window, do not declare success until a real session completes capture, retrieval, and restart persistence.

**Rollback conditions:** integrity failure, namespace leak, missing authoritative context, failed turn capture, failed restart persistence, or material retrieval regression.

**Rollback action:** stop candidate writers, export candidate-only completed turns from the cutover high-water mark, run the proven exactly-once v6→v11 delta translator against a copy, verify it, then restore the old endpoint/config and restart the untouched fork database with the reconciled copy. If reconciliation is not proven, keep writers stopped rather than lose turns.

**Gate 9:** Production uses the candidate; the original v11 database and fork-only archive remain immutable and verified until the rollback window closes.
